# 2. REQUIRED ARCHITECTURE

The project MUST follow a **Feature-Based Architecture**.

Do NOT create a traditional architecture such as:

```text
components/
hooks/
services/
utils/
pages/
```

with everything mixed together.

Instead, organize business functionality inside `features`.

Use a structure similar to:

```text
src/
├── app/
│   ├── layout.tsx
│   ├── page.tsx
│   ├── globals.css
│   └── ...
│
├── features/
│   ├── feature-name/
│   │   ├── components/
│   │   ├── hooks/
│   │   ├── services/
│   │   ├── config/
│   │   ├── utils/
│   │   ├── types/
│   │   ├── constants/
│   │   └── index.ts
│   │
│   └── another-feature/
│       ├── components/
│       ├── hooks/
│       ├── services/
│       ├── config/
│       ├── utils/
│       ├── types/
│       ├── constants/
│       └── index.ts
│
├── shared/
│   ├── components/
│   ├── hooks/
│   ├── types/
│   ├── constants/
│   ├── utils/
│   └── ...
│
├── infrastructure/
│   ├── api/
│   │   ├── axios-instance.ts
│   │   ├── interceptors.ts
│   │   └── ...
│   │
│   ├── query/
│   │   ├── query-client.ts
│   │   └── ...
│   │
│   └── ...
│
└── config/
    └── ...
```

Adapt the exact folder names according to the actual features identified from the screenshots, but preserve this architectural philosophy.

---

# 3. FEATURE ISOLATION

Every business domain should live inside its own feature.

For example, if the screenshots contain:

* Authentication
* Dashboard
* Products
* Orders
* Users
* Integrations
* Settings

then structure them as:

```text
features/
├── auth/
├── dashboard/
├── products/
├── orders/
├── users/
├── integrations/
└── settings/
```

Each feature owns its own:

```text
components/
hooks/
services/
config/
utils/
types/
constants/
```

Do NOT move feature-specific logic into `shared`.

Only truly reusable code belongs in `shared`.

---

# 4. SHARED LAYER

The `shared` folder should contain only reusable, business-agnostic code.

Examples:

```text
shared/
├── components/
│   ├── Button/
│   ├── Input/
│   ├── Modal/
│   ├── DataTable/
│   ├── EmptyState/
│   ├── LoadingState/
│   └── ...
│
├── hooks/
│   ├── useDebounce.ts
│   ├── useMediaQuery.ts
│   └── ...
│
├── utils/
│   ├── format-date.ts
│   ├── format-currency.ts
│   └── ...
│
├── types/
└── constants/
```

Do not put business-specific components here.

For example:

`ProductCard` belongs in `features/products/components`, NOT `shared/components`.

A generic `Card` belongs in `shared/components`.

---

# 5. INFRASTRUCTURE

Create an `infrastructure` layer for technical concerns that should not belong to a specific feature.

For example:

```text
infrastructure/
├── api/
│   ├── axios-instance.ts
│   ├── interceptors.ts
│   └── api-error.ts
│
├── query/
│   └── query-client.ts
│
└── ...
```

Create a centralized Axios instance.

Do NOT create multiple Axios instances inside individual features unless there is a strong architectural reason.

Feature services should use the centralized API client.

Example:

```text
features/products/services/product.service.ts
```

should use:

```text
infrastructure/api/axios-instance.ts
```

instead of creating its own Axios instance.

---

# 6. SERVER STATE

Use TanStack Query for server state.

Do NOT use:

```text
useEffect + useState
```

for data fetching when React Query is appropriate.

For each feature, keep query/mutation logic inside feature hooks.

Example:

```text
features/products/
├── hooks/
│   ├── use-products.ts
│   ├── use-product.ts
│   ├── use-create-product.ts
│   └── use-update-product.ts
│
└── services/
    └── product.service.ts
```

Keep API communication separate from UI components.

Components should NOT contain raw Axios calls.

---

# 7. COMPONENT DESIGN

Build reusable components based on the screenshots.

Avoid creating one giant component such as:

```text
Dashboard.tsx
```

containing the entire page.

Break the UI into meaningful components.

For example:

```text
features/dashboard/
├── components/
│   ├── DashboardHeader.tsx
│   ├── StatsCards.tsx
│   ├── StatsCard.tsx
│   ├── RecentActivity.tsx
│   ├── ActivityItem.tsx
│   └── ...
```

Components should have a single clear responsibility.

---

# 8. NEXT.JS APP ROUTER

Use the App Router correctly.

Keep route files inside:

```text
src/app/
```

but keep business logic inside `features`.

For example:

```text
app/
├── dashboard/
│   └── page.tsx
│
features/
└── dashboard/
    ├── components/
    ├── hooks/
    ├── services/
    └── ...
```

The route page should mainly compose the feature rather than contain all business logic.

Example:

```tsx
import { DashboardPage } from "@/features/dashboard";

export default function Page() {
  return <DashboardPage />;
}
```

---

# 9. BARREL EXPORTS

Use feature-level barrel exports when useful.

Example:

```text
features/products/index.ts
```

Then:

```tsx
import { ProductsPage } from "@/features/products";
```

Avoid unnecessarily deep imports when a clean public feature API can be provided.

---

# 10. TYPESCRIPT

Use strict TypeScript.

Avoid:

```tsx
any
```

unless absolutely unavoidable.

Create proper domain types inside the relevant feature:

```text
features/products/types/
```

Do not create one giant global types file containing all application types.

---

# 11. CONFIGURATION

Feature-specific configuration belongs inside:

```text
features/<feature>/config/
```

Application-wide configuration belongs outside features.

For example:

```text
features/integrations/config/integration-config.ts
```

while global environment/API configuration belongs to:

```text
config/
```

# 16. API LAYER

Assume the backend will be connected later.

Example:

```text

```

  getProducts: async () => {},
